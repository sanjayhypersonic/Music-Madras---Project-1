# Music Madras — research report for the settings, editorial, visibility and notification architecture

Date: 2026-10-21. Branch `music-madras-production-rebuild`. This report separates **external recommendations** (cited), **decisions already established by Music Madras**
(from the repository and prior phases) and **repository facts verified in this task**. Source pages were fetched and summarized on 2026-10-21; they are cited by URL, not quoted.

## 1. Repository facts verified in this task

- **Settings:** the only database-backed configuration is `SyncPolicy` (sync-only). Studio Settings (`app/(studio)/studio/(protected)/settings/page.tsx`) is read-only profile/security text and says connections are set in the deployment. Deployment configuration is environment variables (`modules/config/siteOrigin.ts`, `productionConfig.ts`).
- **`EditorialContent`** (`prisma/schema.prisma`): `slug`, `title`, `body`, `archivedAt`, media link. **No repository, Studio screen or public reader exists.** It has no status, published snapshot or SEO fields.
- **Safe rendering:** there is **no Markdown renderer** in the repository. `app/(museum)/learning/[slug]/page.tsx` splits stored text into paragraphs and renders them as React text (no HTML injection).
- **Visibility:** `modules/mmke/catalogue/isYouTubeVideoPagePublic.ts` is the single predicate: published, unarchived page; `OBSERVED` video; `public`, or `unlisted` with `unlistedPublicationApprovedAt`. `YouTubeVideoPage.unlistedPublicationApprovedAt` has no recorded approver (audit entry only).
- **RBAC** (`modules/auth/policy.ts`): `RECORDING_PUBLISH` (Administrator and above) is "who may change what visitors see" (6J-1 rule); `CATALOGUE_WRITE` edits; `EDITORIAL_REVIEW` reviews; `SETTINGS_MANAGE` (Super Administrator, Founder) administers.
- **View statistics:** the sync overwrites `YouTubeVideo.currentViewCount` and `statisticsUpdatedAt`; **no history is kept**. `YouTubeAnalyticsObservation` exists (period, metric, value) but the analytics sync is not wired into any route or script, so **view trends are not available** and must not be assumed.
- **Notifications:** none exist. Email is `modules/auth/email/emailProvider.ts` (SMTP, invitations and resets only; production refuses to fall back to the console).
- **AI:** provider-neutral gateway (`modules/ai`), Recording-only `ContentSuggestion` workflow, evidence-id citation validation, no interview mechanism.
- **Validation:** no schema-validation library is installed (no Zod). **Scheduler:** none; hosting is not selected.
- **Tests:** isolated Postgres integration suite (`npm run test:integration`, test DB marker guard).

## 2. External research and what it implies

| Topic | Source | Finding | Implication for Music Madras |
|---|---|---|---|
| YouTube visibility semantics | YouTube Help, "Change video privacy settings" — <https://support.google.com/youtube/answer/157177> | Unlisted: anyone with the link can watch; not on the channel, subscriber feeds or recommendations; **can be placed in public playlists**; search only if in a public playlist. Private is shareable only to named viewers. | Unlisted-in-a-playlist is normal on YouTube, so **YouTube playlist membership must never imply approval**. Private never becomes public. |
| API fields | YouTube Data API, Videos resource — <https://developers.google.com/youtube/v3/docs/videos> | `status.privacyStatus` is `private` / `public` / `unlisted`; `viewCount`, `likeCount`, `commentCount` are statistics; from **2026-08-24** `viewCount` counts when playback begins for **all formats including Shorts**. | The visibility model maps one-to-one onto the API field. Cross-format and cross-date view comparisons need care; ranking must be bounded and explainable. |
| Helpful content | Google Search Central, "Creating helpful, reliable, people-first content" — <https://developers.google.com/search/docs/fundamentals/creating-helpful-content> | Original information, substantial value, evident sourcing and expertise; warning signs: search-first content, heavy automation without value, chasing word counts, faking freshness; transparency about AI use. | **No word-count rule.** The quality rubric tests purpose, original editorial context, sourcing and accuracy. |
| Thin / scaled content | Google spam policies — <https://developers.google.com/search/docs/essentials/spam-policies> | Scaled content abuse (mass-produced, unoriginal pages, including via AI), thin pages, near-duplicates. | A playlist page without genuine editorial content must not be published; bulk drafts are acceptable, bulk publication is not. |
| Structured data | Search Central VideoObject — <https://developers.google.com/search/docs/appearance/structured-data/video>; general guidelines — <https://developers.google.com/search/docs/appearance/structured-data/sd-policies> | Required `name`, `thumbnailUrl`, `uploadDate`; recommended `embedUrl`, `duration`, `description` unique per video; markup must describe visible content and not mislead. | Existing `VideoObject` markup stays; playlist markup lists only visible members; no canonical-entity markup without a canonical relationship. |
| Pagination | Search Central — <https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading> | Crawlable `<a href>` links, unique URL per page, **each page its own canonical**, `rel=prev/next` unused; filtered/re-sorted variants should be `noindex` or blocked. | `/videos?page=n` self-canonical; search/filter variants `noindex,follow`. |
| Faceted navigation | Search Central — <https://developers.google.com/search/docs/crawling-indexing/crawling-managing-faceted-navigation> | Filter combinations create near-endless URLs; block or canonicalise to the unfiltered listing; 404 for nonsensical combinations. | Same; facet options are derived from the eligible set, impossible combinations return the empty state, not new indexable pages. |
| Accessibility | W3C WCAG 2.2, Understanding 2.4.1 Bypass Blocks — <https://www.w3.org/WAI/WCAG22/Understanding/bypass-blocks.html> | Level A: a mechanism to bypass repeated blocks; skip link (G1) or landmarks/headings. | Add a skip link; keep landmarks. |
| Authorization | OWASP Authorization Cheat Sheet — <https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html> | Deny by default; least privilege; validate on every request server-side; object-level checks; central failure handling; test authorization. | Every setting declares its required action; every Server Action re-checks; unauthorized changes are tested. |
| Audit logging | OWASP Logging Cheat Sheet — <https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html> | Log who/what/when/outcome; never log secrets, tokens, connection strings; sanitise entries. | Audit records carry actor, before/after, outcome; **settings can never hold secrets**; audit payloads are validated values only. |
| Config vs toggles | Twelve-Factor, "Config" — <https://12factor.net/config>; Fowler, "Feature Toggles" — <https://martinfowler.com/articles/feature-toggles.html> | Config that varies per deploy lives in the environment (credentials, hostnames); internal wiring stays in code. Toggles differ by longevity and dynamism (release, ops, permissioning, experiment); keep their number low and remove them. | Deployment/secret values stay in env; editorial presentation preferences are typed DB settings; **no generic toggle store, no permissioning-by-setting**; every setting has an owner and a reason, and kill-switch style options are ops settings with a named owner. |
| Draft vs published | Sanity docs, "Drafts" — <https://www.sanity.io/docs/content-lake/drafts> | Draft and published are separate stored states; publish copies draft to the live document; later edits do not touch live content; keep an explicit `publishedAt`. | `EditorialContent` and playlist pages get published snapshots; the public site reads snapshots only; `publishedAt` is set by the publish action. |
| Recency scoring | Elastic function-score decay — <https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-function-score-query> | Bounded decay (origin, offset, scale, decay) keeps the multiplier in 0..1 and explainable; popularity via a log-style modifier (`log1p`) avoids unbounded dominance; cap the combined boost. | Automatic ranking = bounded recency decay × log-scaled views, with a stated half-life; no opaque model. |
| Small-sample ranking | Evan Miller, "How Not To Sort By Average Rating" — <https://www.evanmiller.org/how-not-to-sort-by-average-rating.html> | Naive scores mislead with small samples; account for uncertainty. | Counts are used only as ordering evidence, and ties break deterministically; **likes/comments are not used** (unreliable ratios on small counts). |
| Alerting | Google SRE Book, "Monitoring Distributed Systems" — <https://sre.google/sre-book/monitoring-distributed-systems/> | Every alert must be actionable and worth interrupting for; avoid noisy, repeated alerts; email alerts for sub-critical issues become noise. | One notification per distinct, unchanged condition; digest-style, with the action link; resolved when the condition clears. |
| Retries | AWS Builders' Library, "Timeouts, retries and backoff with jitter" — <https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter> | Bounded retries with exponential backoff and jitter; only idempotent operations are safe to retry; idempotency tokens. | Delivery attempts are bounded, backed off and recorded; a unique dedupe key makes creation idempotent. |
| Idempotency | Stripe, "Idempotent requests" — <https://docs.stripe.com/api/idempotent_requests> | A client-supplied unique key makes retries return the original result; compare parameters to detect misuse. | `dedupeKey` (unique) on notifications; a repeat call updates, never duplicates. |
| LLM grounding | Anthropic, "Reduce hallucinations" — <https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations> | Allow "I don't know"; restrict to provided documents; cite per claim and **retract claims without support**; these reduce but do not eliminate errors, so validate. | The existing evidence-id validation extends to editor inputs; unsupported claims are flagged and removed from drafts, never published; a human approves. |
| AI governance | NIST AI Risk Management Framework — <https://www.nist.gov/itl/ai-risk-management-framework> (overview page only; it did not detail oversight) | Voluntary framework for trustworthy AI; the overview does not specify oversight mechanisms. | Human-in-the-loop is a Music Madras decision (below), not derived from NIST. |
| Migrations | Prisma data-migration guidance — <https://www.prisma.io/docs/orm/prisma-migrate/workflows/data-migration> | Add columns as nullable first, backfill separately, enforce last; do not edit applied migrations; PostgreSQL migration runs in one transaction. | All migrations here are additive (new tables, nullable or defaulted columns); never edit an applied migration. |

**Not found / limits of the research:** the NIST overview does not describe human-oversight mechanisms; no authoritative source defines a "right" cadence for reviewing unlisted videos or a numeric quality threshold for cultural-archive pages — those are Music Madras decisions made configurable and explainable.

## 3. Decisions already established by Music Madras (reused, not re-decided)

- Archive at the foundation, discovery at the surface; a YouTube video, playlist, Recording and Collection are distinct objects.
- `RECORDING_PUBLISH` governs anything that changes what visitors see; AI never publishes, approves sources or rights, or selects real-world photographs.
- Unlisted videos may be exposed only through **explicit, recorded** approval; approval is never inferred from YouTube playlist membership.
- No hardcoded business content; an exception register documents what stays in code.

## 4. Consequences for the design (summary; details in `docs/architecture/ADR-0002-settings-editorial-and-visibility.md`)

1. Typed, registry-driven settings (code-defined definitions, database-stored values, per-setting authorization, atomic audited updates); secrets and visibility/rights/security invariants are **not** settings.
2. `EditorialContent` gains a draft/published lifecycle with published snapshots, history and SEO fields.
3. A shared eligibility service defines distinct surfaces (page, discovery, playlist) so unlisted exposure is scoped, recorded and revocable.
4. A small in-Studio notification system with deduplication and honest delivery status; email only when configured.
5. Hybrid featured content: pinned editorial selections first, bounded explainable automatic fill, same eligibility everywhere.
6. Playlist pages are published only after an explainable, configurable quality rubric passes on the **current** content; AI asks focused questions and drafts only from supplied data and approved evidence.
